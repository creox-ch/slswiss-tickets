# Чек-лист перед запуском автоматизации у швейцарского клиента

> Копировать целиком в проект клиента и заполнять. Смысл не в том, чтобы «быть в порядке
> с законом» — а в том, чтобы **не переделывать архитектуру после подписания договора**
> и не спорить с юристом клиента в момент, когда всё уже работает.
>
> Для корпоративного клиента этот заполненный файл сам по себе — аргумент: он показывает,
> что подрядчик понимает, где живут данные. Обычно на этом закрывается половина вопросов
> их compliance-отдела.

**Проект:** ……
**Клиент (юрлицо, адрес):** ……
**Заполнил / дата:** ……

---

## 0. Быстрая сортировка: нужен ли вообще весь пакет

Ответьте на три вопроса. Если все три «нет» — хватит короткого раздела в договоре.

- [ ] В систему попадают данные **живых людей** (не только цифры компании)?
- [ ] Данные **покидают** инфраструктуру клиента (наши сервисы, облака, AI)?
- [ ] Есть данные **сотрудников, клиентов или заявителей**, а не только публичные?

Хотя бы одно «да» → идём дальше.

## 1. Роли

- [ ] **Controller (решает зачем и как):** …… — обычно клиент
- [ ] **Processor (обрабатывает по поручению):** Creox
- [ ] **Субпроцессоры:** Supabase, Vercel, Resend, Payrexx, Google — уточнить по проекту (см. [`PROCESSORS.md`](PROCESSORS.md))
- [ ] Клиент **знает и письменно согласен**, что мы привлекаем этих субпроцессоров
- [ ] Если данные идут в **чужую** систему (CRM клиента, их Google Drive) — там контролёр они, мы туда только пишем

⚠️ Частая ловушка: клиент считает, что раз платит нам — мы отвечаем за всё.
Это ровно наоборот. Проговорить на старте, письменно.

## 2. Инвентарь данных

Заполнить таблицу — без неё остальные пункты гадание:

| Категория | Поля | Откуда | Зачем | Срок хранения |
|---|---|---|---|---|
| напр. заявки с сайта | имя, email, телефон, текст | форма | связаться | 24 мес |
| …… | …… | …… | …… | …… |

- [ ] Есть ли **особо ценные данные** по revDSG: здоровье, религия, политвзгляды,
      расовое/этническое происхождение, биометрия, генетика, административные/уголовные
      производства, меры социальной помощи, профсоюз? → если да, планка выше: явное согласие, узкий доступ
- [ ] Есть ли данные, которые *формально* не особо ценные, но по факту чувствительные:
      **финансы, зарплаты, долги, психологические тесты, оценка личности**? → обращаться как с особо ценными
- [ ] Есть ли **данные детей**? → отдельный разговор
- [ ] Собираем ли мы **больше**, чем нужно для цели? Убрать лишние поля из формы —
      самая дешёвая мера защиты за всё время проекта

## 3. Карта потоков

- [ ] Нарисована цепочка: откуда → через что → где лежит → кто читает
- [ ] Указаны **все** промежуточные звенья, включая почту и мессенджеры команды
- [ ] Отмечено, где данные **хранятся**, а где только **проходят** (это разные обязанности)
- [ ] Отмечено, что попадает в **логи** (логи — тоже хранилище)

Пример нашей типовой цепочки:
`Форма на сайте → POST /api/forms (Vercel, США) → Supabase (Ирландия) → Resend (письмо) → Google Workspace (ящик)`

## 4. Внешние сервисы

Для каждого — строка в реестре:

| Сервис | Роль | Где серверы | DPA | Проверено |
|---|---|---|---|---|
| …… | процессор / субпроцессор | …… | ✅/❓ | дата |

- [ ] У каждого сервиса **принят/подписан DPA** (у большинства это кнопка в дашборде, а не переговоры)
- [ ] Проверено, что **тарифный план** допускает коммерческое использование и даёт DPA
      (у ряда провайдеров DPA только с платного плана — легко напороться)
- [ ] Проверен **срок хранения логов** у каждого сервиса
- [ ] AI-провайдеры отдельно: что именно уходит в модель, обучается ли провайдер на этих данных,
      есть ли zero-retention. Для Anthropic/OpenAI на бизнес-планах обучение на данных API по умолчанию не ведётся —
      **но это надо подтвердить по актуальным условиям вашего плана, а не по памяти**

## 5. Трансграничная передача

- [ ] Список: что уходит за пределы Швейцарии
- [ ] **ЕЭЗ** — в списке стран с адекватной защитой (Швейцария признаёт ЕС) → дополнительных гарантий обычно не требуется
- [ ] **США и прочие** → нужны SCC + швейцарское дополнение (Swiss addendum) в DPA провайдера
- [ ] Если клиент — банк, страховая, врачебная практика, госструктура → **отраслевые требования жёстче**,
      возможен запрет на выход данных из Швейцарии вообще. Спросить **до** выбора стека, а не после

## 6. Документы

Отметить, что нужно именно этому проекту (полный пакет нужен редко):

- [ ] Договор на разработку / услуги
- [ ] NDA
- [ ] **DPA (Auftragsverarbeitungsvertrag)** — если мы процессор. Почти всегда да
- [ ] Datenschutzerklärung на сайте
- [ ] Impressum (по швейцарскому UWG обязателен для коммерческих сайтов)
- [ ] AGB — если есть продажи
- [ ] Перечень субпроцессоров (приложение к DPA)
- [ ] TOMs (приложение к DPA) — базу брать из [`TOMS.md`](TOMS.md)
- [ ] Политика хранения и удаления
- [ ] Cookie-баннер + управление согласием — если есть аналитика/маркетинговые скрипты

## 7. Безопасность

- [ ] Кто имеет доступ к боевым данным — поимённо
- [ ] **2FA включена** у всех: GitHub, хостинг, база, почта, платёжный провайдер
- [ ] Секреты не в репозитории; репозиторий не публичный, если в нём есть что скрывать
- [ ] У подрядчиков — минимальные права (не «владелец проекта» по умолчанию)
- [ ] Бэкапы: есть, известна глубина, **проверено восстановление** (бэкап без теста восстановления — не бэкап)
- [ ] Доступ **отзывается при уходе** человека из проекта — есть список, что именно отзывать
- [ ] Есть план на инцидент: кто решает, кого уведомляем, в какой срок (см. [`DOC-TEMPLATES.md`](DOC-TEMPLATES.md))

## 8. Отдельно: AI в потоке данных

Если в цепочке есть LLM (генерация ответов, классификация заявок, чат-бот):

- [ ] Что именно уходит в модель — весь текст заявки или очищенный минимум?
- [ ] Можно ли **удалить персданные до отправки** (маскирование email/имени)? Если да — сделать
- [ ] Провайдер назван в Datenschutzerklärung как получатель
- [ ] Клиент знает, что его данные проходят через AI-провайдера, и согласен письменно
- [ ] Решения, влияющие на человека (отказ, скоринг, отбор), **не принимаются автоматически без участия человека** —
      это отдельно регулируется и в revDSG, и в GDPR
- [ ] Права доступа **агента-разработчика** к боевой базе ограничены: не выгружать реальные
      персданные в контекст модели без необходимости
